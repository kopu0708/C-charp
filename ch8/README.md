# 챕터 8은 인터페이스와 추상 클래스 관련 내용이다.

사실 작년 즈음인가 공부하다가 기본 문법정도만 때고 학교 공부하랴 훈련소 갔다오랴 하며 쭉 안했었는데 공익 생활 하면서 게임 만들어보니깐 모르는게 너무 많았다. 

특히 인터페이스는 아예 뭔지도 몰라서 책을 다시 거의 반년만에 폈는데 클래스 내용도 읽어보니깐 모르겠어서 복습차원으로 쭉 공부하고 드디어 인터페이스 파트다.

아무튼 인터페이스는 뭐냐? 생긴건 일단 클래스랑 비슷하다. interface 키워드를 이용해서 선언한다.

메소드, 이벤트, 인덱서, 프로퍼티만을 가질 수 있다.  이게 뭔데요? 나중에 알아보자 적어도 메소드는 뭔지 아니깐 

인테페이스는 접근 제한 한정자를 사용할 수 없고 모든 것이 public으로 선언된다. 그리고 메소드 이벤트 등만 가질 수 있다 했는데 그마저도 구현부가 없다.

인터페이스는 인스턴스를 가질 수 없지만 이 인터페이스를 상속받는 클래스의 인스턴스를 만드는 게 가능하다. 물론 규칙이 있다. 파생 클레스는 인터페이스에 선언된 모든 메소드를 구현해줘야 한다.

이 메소드들은 public 한정자로 수식해야한다. 간단한 예제를 보고가자 [예제1](01_InterfaceEx.cs)

예제 처럼 interface 키워드로 선언 그리고 내부에 구현할 메소드 이름과 매게변수만 써 놓고 해당 인터페이스를 상속 받는 클래스에서 메소드를 구현하는 흐림인걸 보았다.

인터페이스는 인스턴스를 못 만들지만, 참조를 만들 수 있다. 이 참조에 파생 클래스의 객체의 위치를 담는 것이다. 파생 클래스는 기반 클래스 와 같은 형식으로 간주되듯이 

인터페이스와 클래스 관계에도 적용된다. 근데 이걸 왜 쓰나요?

클래스가 따라야 하는 약속 같은 것이다. 인터페이스는 자신으로부터 파생될 클래스가 반드시 메소드를 구현하도록 강제한다. 

어떤 클래스든 해당 인터페이스에 선언된 메소드를 구현하면 해당 인터페이스의 역할을 할 수 있다.  

또한 인터페이스의 상속은 여러 클래스에 걸쳐 할 수 있다. 즉 같은 인터페이스를 상속 받아도 클래스 마다 메소드를 다르게 구현 할 수 있다는 말이다. 난 게임개발이 목표이니 게임을 예시로 예제로 만들어 보겠다. [예제2](02_InterfaceEx.cs)

### 인터페이스의 아들 인터페이스 
인터페이스를 상속할 수 있는 것은 클래스뿐 만이 아니다. 구조체는 물론이고, 인터페이스도 인터페이스를 상속할 수 있다.

인터페이스에 기능을 추가하고 싶다던가 할 때 상속받는 인터페이스를 하나 더 만들면 된다. 아니 그냥 수정하면 안됨? 

그래도 좋지만은 안타갑게도 그럴 수 없는 경우도 있다. 우리가 메소드 숨기기를 했던 것 처럼 수정하고 싶은 소스 코드가 어셈블리로만 제공되는 경우가 그렇다. 

또한 이미 인터페이스를 상속 받아 정상적으로 실행되는 클래스들이 한 100개 즈음 있다 치자 이걸 하나하나다 수정하는 것은 상당한 모험이 될 것이다. 그냥 인터페이스를 상속하는 인터페이스를 하나 만드는게 좋다.

### 여러 인터페이스. 한꺼번에 상속하기 
클래스는 여러 클래스를 한꺼번에 상속할 수 없다. '죽음의 다이아몬드'라는 문제가 있는데 자세한 건 ai한테 물어보고 아무튼 이게 클래스가 다중 상속을 받지 못하는 이유다. 

그래서 인터페이스를 쓴다. 인터페이스는 다중 상속이 가능하기 떄문에 왜냐? 앞서 말했듯이 인터페이스는 틀만 잡아주고 구현은 하지 않는다. 즉 어떤 메소드를 불러올지 햇갈리지 않는다.

예제를 알아보자 [예제4](04_MultInterface.cs)

그럼 여러 클래스로부터 구현을 물려받는건 곧 죽어도 안되겠네요? 

그건 아니다 포함(Containment)라는 기법도 있다. 이 기법은 클래스 안에 물려받고 싶은 기능을 가진 클래스들을 필드로 선언해 넣는 것이다.

그럼 메소드를 만들고 구현부에 필드를 가져와 메소드를 호출 하면 되겠죠? 

~~~
MyVehicle()
{
  Car car = new Car();
  Plane plane = new Plane();
  public void Fly() {plane.Ride();}
  public void Run() {car.Ride();}
}
~~~

### 인터페이스의 기본 구현 메소드 
인터페이스에 선언하는 메소드는 구현부가 없었다. 틀만 잡아주는 거지 자세한 구현은 클래스의 일이였기 때문이다. 

그런데 어떤 서비스를 한 10년 동안 했다 치자. 그동안 수많은 업데이트와 수정을 거쳐 기본 인터페이스를 상속받는 클래스도 업그레이드 되고 인터페이스의 파생 클래스가 수도 없이 생겼다.

이런 코드를 레거시 코드라고 하는데 업그레이드할 떄 각별히 주의 해야한다. 만약 이 기존의 기본 인터페이스를 수정하고 싶어 메소드를 추가했다. 이제 그러면 모든 코드를 다시 손봐야 할 것이다.

파생 클래스는 인터페이스의 모든 메소드를 구현하는 것이 기본 규칙이기 때문이다. 

이럴 때 쓰는게 기본 구현 메소드이다. 인터페이스에 새로운 메소드를 추가할 때 기본적인 구현체를 갖도록 해서 기존에 있는 파생 클래스에서의 컴파일 에러를 막는다.

또한 기본 구현 메소드는 인터페이스 참조로 업캐스팅했을 때만 사용할 수 있다 파생 클래스에서 인터페이스에 추가된 메소드를 엉뚱하게 호출할 가능성도 없다.

인터페이스에 선언된 기본 구현 인터페이스는 파생 클래스의 참조로 호출할 수 없다. [예제5](DefaultIInterface.cs) 

햇갈릴 것 같으니 기억해두자 기본 구현 메소드는 반드시 인터페이스 참조로 업캐스팅 했을 때만 사용가능하다.
